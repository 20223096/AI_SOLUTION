# Noise Impact 신뢰성 검증 및 일정 목적함수 비교

## 1. 범위와 버전

검증일은 2026-10-24이다. 기존 `absolute_impact`, `incremental_impact`, 기본 `objective_mode=incremental_impact`, 후보 생성과 제약은 유지했다. 기존 점수식은 `legacy_v1`, 추가 지표 묶음은 `robust_experimental_v1`로 응답한다. 아래 수치는 코드를 실제 실행한 결과이며 법정 소음평가나 주민 피해의 실증값이 아니다.

실제 시나리오 ID는 C가 `scenario-c-exam`, D가 `scenario-d-restricted`이다. 본 문서의 CASE C/D는 이 ID를 뜻한다.

## 2. 07:00 추천 원인의 분해

### A. 물리적 에너지 합산

합성은 `10 log10(Σ10^(L/10))`이다. B 08:00 창천중에서 기존환경 82.37 dB와 신규 공사 63.58 dB를 합치면 82.43 dB이고 증가는 0.06 dB다. 신규 공사 음원은 사라지지 않았지만 기존환경보다 약 19 dB 낮아 합성 레벨 차이가 작다. A/B의 공사 단독 에너지 노출은 모두 `132.021053` 65 dB 기준 에너지·분이다.

### B. legacy level component 절단

`level=clip((L-55)/30, 0, 1)`이므로 85 dB부터 level 성분이 포화한다. 공식 세 수음점에서 A/B 원 일정은 최대 72.15/82.43 dB라 level 포화 슬롯은 각각 0개다. A의 60개, B의 68개 경고 슬롯은 작은 양의 물리 증가가 Impact 소수 둘째 자리에서 0으로 반올림된 경우다. 따라서 B의 7.36을 만든 주원인은 85 dB 절단이 아니라 에너지 합산 마스킹과 점수 해상도다. 85 dB 이상의 별도 검증에서는 level 절단으로 추가 정보가 실제 손실된다.

### C. 민감도 가중치

학교·병원에 적용되는 +0.5는 검증된 영향계수가 아닌 `assumed` 정책값이다. 민감도를 끄면 A 원 일정 증분 Impact는 13.72→12.44, B는 7.36→6.60이다. 민감도는 물리 dB나 공사 에너지를 바꾸지 않는다. A/B의 원시 민감노출은 1620 receptor-minutes, 가정 가중 결과는 2430 weighted receptor-minutes다.

### D. 작업시간과 장비 활성

절단 60분, 브레이커 120분, 굴착 300분, 다짐 60분으로 총 540분이며 15분 슬롯 수는 각각 4/8/20/4다. 순차 공정이라 최대 연속 신규 공사시간은 540분, 07:00~18:00 중 비가동시간은 120분이다. 시간 이동만 하는 9개 후보에서는 장비·거리·운전시간이 같아 공사 단독 에너지와 연속시간이 동일하다.

### E. 기존 이벤트의 위치와 시간

B의 82 dB 이벤트는 07:00~09:00에 공식 수음점 3곳에 동일하게 적용한 가정이다. 원 일정은 3곳×120분=`360 receptor-minutes` 중첩되고 09:00 시작은 0이다. 공공 공사·행사는 날짜 중첩을 `calendar_overlaps`로 반환하지만 일일 시간과 음향값이 검증되지 않아 합성하지 않는다.

### F. 중복 가정

82 dB, 시간, 세 수음점 동일 적용 모두 실측이 아니다. `final-demo-congestion`만 `allow_assumed_event_acoustics=true`로 명시적으로 opt-in한 시뮬레이션이며 응답은 `assumed_simulation_opt_in`을 표시한다. 일반 시나리오는 `verified_public` 시간·음향 이벤트만 합성한다. 따라서 B는 정책 실험이지 실제 기존 공사의 음향 재현이 아니다.

### G. 변경부담

기존 `change_cost`는 **각 작업 시작 이동의 절댓값 합계**다. 전체 공사 시작 이동과 다르다. `offset-120`은 네 작업이 각각 120분 이동해 `change_cost=480분`이지만 프로젝트 시작과 종료 이동은 각각 120분이다. API는 작업별 이동, 합계, 프로젝트 시작/종료 이동, 종료시각, 선행순서, 자원충돌을 분리해 반환한다.

결론적으로 B에서 07:00은 legacy 증분 Impact도 낮고 변경부담도 0이어서 09:00을 지배한다. 이는 “높은 소음에 공사를 겹치는 것이 물리적으로 더 좋다”는 뜻이 아니라 legacy 정책점수가 기존환경 대비 차이만 평가한 결과다.

## 3. 대체 지표 정의

### 신규 공사 음향 노출

수음점·슬롯별 공사 단독 Lp에 대해 다음을 합산한다.

```text
E65 = Σ 10^((Lp_project - 65)/10) × active_minutes
```

단위는 `65 dB-reference energy-minutes`이다. dB를 산술 합산하지 않으며 배경·기존 이벤트는 포함하지 않는다.

### 민감시간 노출

- `sensitive_new_project_receptor_minutes`: 가정 민감도가 1보다 큰 수음점의 원 노출분
- `sensitivity_weighted_new_project_receptor_minutes`: 원 노출분×가정 가중치
- 각 슬롯의 `sensitivity.weight_status=assumed`와 원 가중치 세부항을 함께 반환

시험기간·학교·병원·주거 휴식 가중치는 정책 합의 전 가정이며 물리 노출과 분리한다.

### 연속 노출

- `max_continuous_new_project_minutes`: 신규 장비가 하나 이상 연속 활성인 최장시간
- `new_project_inactive_minutes`: 분석구간 중 신규 장비 비가동시간
- 기존 `longest_quiet_window_minutes`는 전체 환경 기준이므로 별도 유지

연속시간과 생활 불편 사이의 영향계수는 적용하지 않았다.

### 기존 일정 중첩

- `calendar_overlaps`: 날짜 기준 공공 일정, 시간·음향 검증 여부, 합성 가능 여부
- `existing_noise_overlap_receptor_minutes`: 음향 시뮬레이션 이벤트와 신규 공사가 동시에 활성인 수음점별 시간
- `existing_event_acoustic_policy`: 검증 이벤트/가정 이벤트 허용 여부

중첩 정책비용은 목적함수에 넣지 않았다.

### 일정 변경

- `task_start_shift_minutes`: 작업별 시작 이동
- `total_task_start_shift_minutes`: 위 값의 합, 기존 `change_cost`와 동일
- `project_start_shift_minutes`: 전체 공사 시작 이동
- `project_end_shift_minutes`: 전체 공사 종료 이동
- `candidate_project_end`, `predecessor_order_preserved`, `resource_conflicts`

## 4. 목적함수

| 목적 | API 모드 | 축 |
|---|---|---|
| A | `incremental_impact` | legacy 증분 Impact, 작업별 이동합 |
| B | `physical_energy` | E65 공사 에너지·분, 작업별 이동합 |
| C | `sensitive_exposure` | 원시 민감 receptor-minutes, 작업별 이동합 |
| D | `multi_axis` | E65, 원시 민감노출, 연속 공사시간, 작업별 이동합 |

Objective D는 네 단위를 더하거나 정규화하지 않고 다차원 Pareto 지배만 계산한다. epsilon이나 허용범위는 정책 근거가 없어 확정하지 않았다.

## 8. 검증용 가정 시나리오

모두 실제 관측이 아닌 테스트 전용 가정이다.

1. 배경 50 dB + 신규 75 dB: 공사 E65는 15분당 150으로 유지된다.
2. 배경 70 dB + 신규 75 dB: 같은 E65이며 합성 증가만 작아진다.
3. 배경 85 dB + 신규 75 dB: 같은 E65이며 legacy 포화 가능성을 검증한다.
4. 82 dB 동시 발생: B offset-0 중첩 360 receptor-minutes.
5. 비동시 발생: B offset-120 중첩 0, 공사 E65는 동일.
6. 민감시간: 06:59 주거 및 시험시간 대학의 `is_sensitive_time=true`.
7. 비민감시간: 07:00 일반 주거 `false`.
8. 변경 불가: `validation-fixed-schedule`은 offset-0만 가능.
9. 병렬 가동: 테스트 입력에서 절단기·브레이커 Lp를 에너지 합산하고 두 task ID를 보존.
10. 서로 다른 시간: 60/120/300/60분이 4/8/20/4 슬롯으로 보존.

## 9. 구조화 추천 근거

각 `recommended_options[]`는 `recommendation_reasons[]`를 갖는다. 각 사유는 `code`, `message`, 계산 필드를 가리키는 `evidence[].field`, 실제 `value` 또는 원 일정 대비 `delta`, `unit`을 포함한다. 계산하지 않은 개선량은 만들지 않는다. Objective D의 참조 후보는 `non_dominated_multi_axis`로 표시하며 단일 정책 최적안이라고 부르지 않는다.

## 10. 장단점과 안정성

- legacy 증분: 기존환경 대비 추가 체감점수를 설명하지만 높은 배경을 회피하기보다 겹치도록 유도할 수 있다.
- 공사 에너지: 배경과 점수 포화에 독립적이지만 장비·거리·시간이 같은 단순 이동을 구별하지 못한다.
- 민감 노출: 시간 정책을 직접 반영하지만 현재 가중치와 학교·병원 전일 민감 가정은 검증되지 않았다.
- 연속 노출: 공정 분할 비교에 유용하지만 현재 순차 540분 후보에서는 불변이다.
- 다목적 Pareto: 단위를 섞지 않지만 목적값이 같은 후보가 많거나 변경축 때문에 원 일정만 남을 수 있다.

현재 자료에서 안정적으로 말할 수 있는 것은 `offset-0`이 변경부담 최소라는 사실과 공사 단독 에너지가 시간 이동에 동일하다는 점이다. 주민 피해 감소 관점에서 07:00 또는 09:00이 우월하다고 실증할 수 없다.

## 11. 데이터와 정책 한계

필요한 추가 합의·자료는 실제 장비 모델과 운전률, 수음점별 배경 실측, 기존 이벤트의 실제 일일 시간과 음향값, 수업·시험·휴식 시간, 연속노출 영향계수, 중첩 회피의 정책 지위, 공정 분할 가능성이다. 이 정보 없이 epsilon, 가중합, 강제 회피시간을 정하지 않았다.

## 12. 자동화 검증

기존 회귀와 신규 검증을 합쳐 `101 passed`다. 에너지 단위, 배경 마스킹, 민감시간 경계, 동시/비동시, 연속노출, 다차원 Pareto, 두 변경량 정의, 포화, API 호환, 결정론, CASE D 불가능, 고정 일정, 병렬 장비, 상이한 작업시간을 포함한다. Python 컴파일과 API 스모크는 별도로 수행한다.
